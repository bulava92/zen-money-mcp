# Правила проекта SHD (zen-money-mcp)

Действуют в /var/www/zen-money-mcp для репозитория markkats/zen-money-mcp.

## Общение и завершение задач
- Писать кратко: результат, изменённые файлы, проверки и блокеры.
- Не писать статус по каждой команде или прочитанному файлу. В чате и Gitea сообщать только о важном этапе, блокере и результате; комментарии Gitea — одно-два предложения.
- Если пользователь пишет «мы закончили», добавить в /var/www/admin/docs/agent-change-transfer.md секцию «## [<Агент: Claude|Codex|Gemini>] Чат: <название> — <ссылка/id сессии>». Ветку определять автоматически (git branch --show-current). Если задача привязана к Gitea — указать номер Issue, иначе «Issue: не привязана». Указать файлы со статусом новый/изменён. Не включать transfer-файл в список или коммит; не завершать без записи. После отдельной команды коммитить только файлы этой секции и удалить её.

## Изменения и безопасность
- Менять только нужное для задачи; исправлять причину, не добавлять обходы, fallback-логику или дублирующее поведение без запроса.
- Не создавать файлы длиннее 1500 строк; при превышении этого порога обязательно декомпозировать на модули, подкомпоненты или сервисы.
- Временные дампы, логи, скриншоты и отчёты хранить в /tmp. Не удалять и не откатывать пользовательские данные без явного разрешения.
- Не читать и не менять prod (/var/www/admin-prod и /var/www/shd-landings-prod), его .env, кэш, файлы и сервисы без явной команды. Деплой, синхронизация, перезапуск и sudo также требуют отдельной команды.

## Git, команды и проверки
- Создавать или переключать task-ветку только по явной просьбе открыть/вести задачу в Gitea. Перед этим проверить git status; если checkout грязный — не переключать ветку и сохранить пользовательские изменения. Историю Git менять, commit, push, amend и rebase выполнять только по отдельной команде.
- Каждый агент коммитит и пушит в Gitea под своим аккаунтом: Claude — `Claude <claude@xyz.su>`, токен `GITEA_TOKEN_CLAUDE`; Gemini — `Gemini <gemini@xyz.su>`, токен `GITEA_TOKEN_GEMINI`; Codex — `Codex <codex@xyz.su>`, токен `GITEA_TOKEN_CODEX`. Передавать имя и email в коммит (через переменные `GIT_AUTHOR_*`/`GIT_COMMITTER_*` или аргументы Git); для push в Gitea (`origin`) аутентифицироваться своим токеном в памяти (`-c http.https://git.shd.guru/.extraHeader="Authorization: token <TOKEN>" -c credential.helper=`), не подставлять `markkats`. Для remote `github` push выполняется через настроенный credential helper GitHub.
- При пакетном коммите незакоммиченных изменений фиксировать исходный список файлов строго на момент команды. Не подхватывать и не коммитить файлы, изменившиеся или появившиеся после фиксации этого пула, и не создавать под них дополнительные коммиты без отдельной явной команды.
- Читать и искать код узко, предпочитая rg и sed; не выводить большие дампы и списки без необходимости.
- Не запускать тесты, сборки, линтеры или браузер без явной просьбы. Изменение файлов само по себе не разрешает проверки.

## Задачи Gitea
- Любые действия в Gitea выполнять только по явной просьбе пользователя. Сам факт работы над кодом, новый чат или завершение работы не запускают ведение задачи и не разрешают автоматически искать/создавать/закрывать issue, менять поля, запускать таймер или писать комментарии. Просьба открыть и вести задачу разрешает необходимые действия только для этой задачи; закрытие всё равно требует отдельной явной просьбы.
- Просьба открыть и вести задачу разрешает вести её поля в рамках этой задачи. Проверить remote `markkats/zen-money-mcp`, найти подходящий открытый issue или создать его и заполнить краткое описание, подходящие существующие метки, подтверждённый проект и этап, исполнителя (свой аккаунт: `gemini`, `claude` или `codex`, если пользователь не указал другого). Для задачи с кодом создать/проверить task-ветку и указать её в issue. Сначала проверить `git status`; на грязном checkout не переключать ветку и сообщить, что поле пока не заполнено. Не подставлять выдуманные значения или `main` вместо task-ветки. Просьба только создать issue сама по себе не запускает учёт времени.
- Для Gitea API репозитория `markkats/zen-money-mcp` использовать `https://git.shd.guru/api/v1`. Каждый агент работает под своим аккаунтом и своим ключом из окружения процесса; если переменная не задана, читать только этот ключ из `/var/www/admin/.env`: Claude Code — аккаунт `claude`, ключ `GITEA_TOKEN_CLAUDE`; Gemini — аккаунт `gemini`, ключ `GITEA_TOKEN_GEMINI`; Codex — аккаунт `codex`, ключ `GITEA_TOKEN_CODEX`. Не использовать чужой ключ. Передавать токен в памяти в заголовке `Authorization: token <GITEA_TOKEN>`; не печатать, не помещать в командную строку, URL или логи и не сохранять в репозитории. Для чтения и создания issues требуются scopes `read:issue` и `write:issue`; доступ аккаунта к репозиторию проверять отдельно. Если токена или прав не хватает, сообщить пользователю; секрет в чат не запрашивать.
- Учёт времени включать только по явной просьбе вести задачу или учитывать время. Таймер вести только для этой задачи, не создавать дубликаты, учитывать фактическую работу без ожидания и бездействия. При явном запросе закрыть задачу остановить её активный таймер и внести итоговое время.
- По отдельной просьбе закрыть задачу обновить её краткое описание по результату и проверить метки, проект, ветку, этап, исполнителя и фактически учтённое время. Этап менять только по подтверждённому ID колонки; проект, метки и исполнителя — только по проверенным значениям. Если обязательное поле не удалось подтвердить или заполнить, не выдумывать его и сообщить пользователю, оставив задачу открытой до решения.
- При пакетном создании и закрытии задач по циклам разработки следовать /var/www/admin/docs/gitea-tasks.md: формировать глобальные задачи по функциональным подсистемам (не на каждый коммит), указывать ветку main (или task-ветку), исполнителя (аккаунт своего агента: `gemini`, `claude` или `codex`), подтверждённый этап (Milestone) и метки. В описание обязательно включать резюме изменений и блок «### Коммиты (<N>)» со списком всех хэшей и сообщений коммитов периода; отработанное время распределять и вносить в штатный таймер Gitea из расчёта 10 ч/рабочий день, после чего закрывать задачи.
- При ведении задачи фиксировать в комментариях Gitea только завершение крупных этапов (одно-два предложения); не отчитываться по отдельным командам. После запрошенного действия кратко сообщить, что заполнено и какие поля остались незаполненными.
